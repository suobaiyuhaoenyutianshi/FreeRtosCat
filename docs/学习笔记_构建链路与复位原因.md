# 学习笔记：构建链路（clone 即可构建、用户源码接入）与复位原因

> 对应 [env.md](env.md) 里的两句话：
>
> 1. 「HAL/CMSIS 已随仓库 `Drivers/` 提供，换机器 clone 后无需安装 STM32CubeF1 包。」
> 2. 「固件读取复位标志后会清除，因此不会把上一次的复位原因误报成本次。」
>
> 这篇笔记回答：**这些机制分别靠什么实现、代码在哪、怎么自己验证。** 共三部分：
>
> 1. 构建为什么与 CubeMX 解耦（预设 + 工具链文件 + 仓库内 HAL）
> 2. `user_sources.cmake` 如何把用户代码接进构建
> 3. 复位原因码怎么产生，为什么不会把上一次的原因误报成这一次

## 第一部分：构建为什么不依赖 CubeMX

先给结论：CubeMX 在这个工程里只是「生成初始化代码的工具」，**不是构建依赖**。构建链路上真正需要的只有三样：

```
cmake --preset Debug
      │
      ├─ 1. 预设：固定生成器 Ninja + 构建目录 + 工具链文件   (CMakePresets.json)
      ├─ 2. 工具链文件：规定交叉编译器、CPU、链接脚本        (cmake/gcc-arm-none-eabi.cmake)
      └─ 3. HAL/CMSIS 源码：已经在仓库里，用相对路径引用     (Drivers/)
```

本机只需要 `arm-none-eabi-gcc`、`cmake`、`ninja` 在 PATH 里，CubeMX 装不装都无所谓。

### 1.1 入口：CMakePresets.json 把「三条命令的参数」固化成一个名字

[CMakePresets.json](../CMakePresets.json) 里有一个隐藏的 `default` 预设：

```json
{
    "name": "default",
    "hidden": true,
    "generator": "Ninja",
    "binaryDir": "${sourceDir}/build/${presetName}",
    "toolchainFile": "${sourceDir}/cmake/gcc-arm-none-eabi.cmake",
    "cacheVariables": {}
}
```

`Debug` 用 `"inherits": "default"` 继承它，只额外设置 `CMAKE_BUILD_TYPE=Debug`。

所以 `cmake --preset Debug` 等价于手工敲：

```powershell
cmake -G Ninja -B build/Debug `
      -DCMAKE_TOOLCHAIN_FILE=<仓库根>/cmake/gcc-arm-none-eabi.cmake `
      -DCMAKE_BUILD_TYPE=Debug
```

三个细节：

- `hidden: true` 表示它只是模板，不能直接 `--preset default`，防止误用。
- `binaryDir` 用了 `${presetName}`，所以 Debug / Release / MinSizeRel 各自有独立目录，互不覆盖；产物固定落在 `build/Debug/CARTESTFreertos.elf`。
- `toolchainFile` 用 `${sourceDir}` 展开成**仓库自身的路径**，不需要用户手工传，也不会写死某台电脑的绝对路径。

### 1.2 核心约定：工具链文件只假设「编译器在 PATH」

[gcc-arm-none-eabi.cmake](../cmake/gcc-arm-none-eabi.cmake) 承担交叉编译的全部约定。按「语句 → 作用 → 少了会怎样」来记：

| 语句 | 作用 | 删掉/写错的后果 |
|---|---|---|
| `set(CMAKE_SYSTEM_NAME Generic)` | 声明目标没有 Windows/Linux 那套主机系统 ABI（裸机/RTOS） | CMake 按 Windows 主机规则生成，行为完全不对 |
| `set(CMAKE_C_COMPILER_FORCED TRUE)` | 跳过 CMake 对编译器的功能探测 | 探测阶段可能报错中断配置 |
| `set(TOOLCHAIN_PREFIX arm-none-eabi-)` + 各编译器 | 指定交叉编译器 | 退化成主机 `gcc`，产出 x86 程序 |
| `set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)` | 编译器自检只「编译」不「链接」 | 裸机没有默认启动文件/libc，自检链接必失败 |
| `set(TARGET_FLAGS "-mcpu=cortex-m3")` | 指定 Cortex-M3 指令集 | 生成 M3 不支持的指令 |
| `-T stm32f103c8tx_flash.ld` | 指定链接脚本（FLASH/RAM 布局） | 链接器不知道内存从哪开始 |
| `--specs=nano.specs` | 用 newlib-nano 精简 C 库 | 代码体积暴涨，可能放不进 64 KB |
| `-ffunction-sections -fdata-sections` + `-Wl,--gc-sections` | 每个函数/变量单独成段，链接时丢掉没用的 | Flash 浪费，占用统计失真 |
| `-Wl,--print-memory-usage` | 链接后打印 FLASH/RAM 用量 | 构建日志里的占用表就没了 |
| `-Wall -Wextra -Wpedantic` | 打开编译警告 | 交付要求的「0 warning」无从谈起 |
| `--start-group -lc -lm --end-group` | 让 C 库/数学库的符号解析与顺序无关 | 偶发 `undefined reference` |

**关键认知**：这个文件里没有任何一行写死「某台电脑」的路径；唯一的外部假设就是 `arm-none-eabi-*` 在 PATH 里。这就是「换机器只需装工具链」的原因。

#### 那「有 FreeRTOS」为什么还写 Generic？

`CMAKE_SYSTEM_NAME` 描述的是**目标平台的 ABI 环境**，不是字面意义上的「有没有操作系统」：

- `Generic` 表示 CMake 不假设目标有 Windows/Linux 那套系统调用、动态库、进程模型；所有代码静态链接成一个 ELF，C 库由 newlib-nano 提供。
- FreeRTOS 是**和你的代码一起编译进同一个 ELF 的内核库**（`freeRTOS/Src/*.c`），它没有向 CMake 暴露任何「系统 ABI」。从 CMake 视角看，它只是一份要链接的代码。
- 如果写成 `CMAKE_SYSTEM_NAME Linux`，CMake 会按 Linux 规则去链接 `-ldl`、`-lpthread`，裸机根本没有这些东西，配置或链接就会失败。

**Generic = 没有主机操作系统的 ABI；FreeRTOS 是被静态链接进来的实时内核，不影响这个判断。**

### 1.3 本工程的 HAL/CMSIS：`Drivers/` 相对路径，没有 `HAL_ROOT`

CubeMX 默认生成的 `cmake/stm32cubemx/CMakeLists.txt` 有时会写成某台电脑的绝对路径，例如：

```cmake
# 换机器就断的写法
set(HAL_ROOT "C:/Users/xxx/STM32Cube/Repository/STM32Cube_FW_F1_V1.8.7/Drivers")
```

本工程没有这一行。HAL/CMSIS 就在仓库的 [`Drivers/`](../Drivers)，CMake 直接用相对路径：

```cmake
set(MX_Include_Dirs
    ${CMAKE_CURRENT_SOURCE_DIR}/../../Core/Inc
    ${CMAKE_CURRENT_SOURCE_DIR}/../../Drivers/STM32F1xx_HAL_Driver/Inc
    ${CMAKE_CURRENT_SOURCE_DIR}/../../Drivers/STM32F1xx_HAL_Driver/Inc/Legacy
    ${CMAKE_CURRENT_SOURCE_DIR}/../../Drivers/CMSIS/Device/ST/STM32F1xx/Include
    ${CMAKE_CURRENT_SOURCE_DIR}/../../Drivers/CMSIS/Include
)
```

HAL 源文件也在 [STM32_Drivers_Src](../cmake/stm32cubemx/CMakeLists.txt#L31-L52) 里逐项列出，路径全部从仓库根派生。

「仓库里自带 HAL」指的就是这棵目录树，clone 完成后本地就有：

```
Drivers/
├─ CMSIS/                       # 内核头文件 + 设备头文件（stm32f103xb.h 等）
└─ STM32F1xx_HAL_Driver/
   ├─ Inc/                      # HAL 头文件
   └─ Src/                      # HAL 源文件（本工程按需编译 18 个）
```

两个事实让链路闭环：

1. `Drivers/` 已被 git 跟踪：`git ls-files Drivers` 共 **80 个文件**。
2. [.gitignore](../.gitignore) 只忽略 `build/`、`*.elf`、`*.map` 等生成物，没有忽略 `Drivers/`，所以不会「本机能编、别人 clone 后缺 HAL」。

> 这和你贴的 `third_party/stm32cube_f1` 是同一原理，只是目录名不同。本工程没有 `HAL_ROOT` 变量，也没有 `third_party/`。

### 1.4 怎么自己验证「真的不依赖」

```powershell
$tmp = Join-Path $env:TEMP "CARTESTFreertos_clone"
if (Test-Path $tmp) { Remove-Item -Recurse -Force $tmp }

git clone <仓库地址> $tmp
Set-Location $tmp

cmake --preset Debug
cmake --build --preset Debug
```

临时目录里没有 `build/`、没有 `compile_commands.json`、也不指向本机 CubeMX 目录。如果仍然 **0 error 0 warning** 并产出 elf，就说明 HAL 确实来自仓库，工具链只依赖 PATH。

本工程 2026-11-17 的实测结果：

```text
Firmware version: baseline-2026-11-16-4-g85669a3
Debug: FLASH 49,704 B (75.84%) / RAM 14,512 B (70.86%)
0 error 0 warning
```

### 1.5 把 `build/` 删了会怎样？

`build/` 里全是生成物：`CMakeCache.txt`、`build.ninja`、`.o`、`.elf`、`.map`、`compile_commands.json`。删掉不会丢源码，只是要重新走一遍配置：

```powershell
Remove-Item build -Recurse -Force
cmake --preset Debug          # 第一步：重新配置，重建 build/Debug
cmake --build --preset Debug  # 第二步：全量编译 + 链接
```

三个要点：

1. **两步都不能省**：`cmake --build` 只是调用 `build/Debug` 里已生成好的 Ninja 工程；目录被删后没有 `CMakeCache.txt`/`build.ninja`，它会直接报找不到构建系统。
2. 删掉 `build/` 再构建，等价于空目录冷构建：没有历史缓存、没有本机痕迹，仍然 0 error 0 warning，才算真正可复现。
3. 整个工程文件夹搬家或改路径后，也必须删 `build/` 重新 configure，因为 `CMakeCache.txt` 里记着旧的源码绝对路径。

### 1.6 本工程额外加的两件事：版本注入与 `size` 目标

这两段在根 [CMakeLists.txt](../CMakeLists.txt)，不是 CubeMX 生成的：

**① 固件版本注入**（第 66–84 行）：

```cmake
set(FW_VERSION "dev")
if(EXISTS "${CMAKE_CURRENT_SOURCE_DIR}/.git")
    execute_process(
        COMMAND git describe --tags --always --dirty
        WORKING_DIRECTORY "${CMAKE_CURRENT_SOURCE_DIR}"
        OUTPUT_VARIABLE FW_VERSION
        OUTPUT_STRIP_TRAILING_WHITESPACE
        ERROR_QUIET
    )
endif()
target_compile_definitions(${CMAKE_PROJECT_NAME} PRIVATE
    FW_VERSION="${FW_VERSION}"
)
```

- 有 `.git` 时，版本号来自 `git describe`，例如 `baseline-2026-11-16-4-g85669a3`。
- 没有 `.git`（源码导出/压缩包）时回退 `dev`，不会因为缺少 git 而配置失败。
- `main.c` 里还有一层 `#ifndef FW_VERSION` 兜底，EIDE 等非 CMake 构建也能编。

**② 每次构建打印 FLASH/RAM**（第 94–107 行）：

```cmake
add_custom_target(size ALL
    COMMAND ${CMAKE_COMMAND}
            -DSIZE_TOOL=${CMAKE_SIZE}
            -DELF=${CMAKE_CURRENT_BINARY_DIR}/${CMAKE_PROJECT_NAME}.elf
            -DFLASH_SIZE=65536
            -DRAM_SIZE=20480
            -P ${CMAKE_CURRENT_SOURCE_DIR}/cmake/print_size.cmake
)
add_dependencies(size ${CMAKE_PROJECT_NAME})
```

- `ALL` 目标不比较时间戳，所以零改动构建也会打印，不会被 `ninja: no work to do` 吞掉。
- `print_size.cmake` 用 `size` 的 `text+data` 算 FLASH、`data+bss` 算 RAM。
- 与 `ld --print-memory-usage` 可能差 4 B（输出段对齐），本文以 `size` 口径为准。

**③ Debug 用 `-Og`**（第 36–42 行）：

```cmake
if(CMAKE_BUILD_TYPE STREQUAL "Debug")
    string(REPLACE "-O0 -g3" "-Og -g3" CMAKE_C_FLAGS "${CMAKE_C_FLAGS}")
    string(REPLACE "-O0 -g3" "-Og -g3" CMAKE_ASM_FLAGS "${CMAKE_ASM_FLAGS}")
endif()
```

CubeMX 的 toolchain 文件给 Debug 配的是 `-O0 -g3`；这个工程用 `-O0` 会超过 64 KB Flash，链接失败后 `.elf` 不生成，调试器就报 `Unable to find executable file`。换成 `-Og` 后体积接近 Release，同时保留源码级调试信息。

### 1.7 什么时候还会用到 CubeMX

只有一种情况：**改硬件配置**（引脚、时钟、外设），用 CubeMX 打开 `.ioc` 重新生成代码。

本工程的风险和 `third_party` 那套不同：

- 没有 `HAL_ROOT` 绝对路径问题；
- 但链接脚本 `stm32f103c8tx_flash.ld` 的 `(READONLY)` 会被冲掉；
- `stm32f1xx_it.c` 可能多出空的 `SVC_Handler`/`PendSV_Handler`；
- PB10/PB11、PB8/PB9 已被蓝牙/MPU6050 占用，不能照抄别的工程。

详见另一份笔记：[CubeMX 重生成与 HAL 随仓库](学习笔记_CubeMX重生成与HAL随仓库.md)。

**一句话：CubeMX 负责生成代码，CMake 负责构建；仓库里自带 HAL，所以构建不需要 CubeMX。**

## 第二部分：`user_sources.cmake` —— 自己写的代码怎么接进构建

### 2.0 它在整个构建里的位置

顶层 [CMakeLists.txt](../CMakeLists.txt) 第 92 行只有一句：

```cmake
include(${CMAKE_CURRENT_SOURCE_DIR}/user_sources.cmake)
```

两个关键后果：

- `include()` 是**文本展开**，不是 `add_subdirectory()`。所以 `CMAKE_CURRENT_SOURCE_DIR` 仍然是仓库根，`CMAKE_PROJECT_NAME`（`CARTESTFreertos`）和可执行目标都在同一作用域里，文件里可以直接引用。
- 分工清晰：`cmake/stm32cubemx/CMakeLists.txt` 负责「CubeMX 生成的文件 + HAL」；`user_sources.cmake` 负责「手写代码 + FreeRTOS 内核 + 头文件路径」。

### 2.1 第 1 段：GLOB 收 `Core/Src` 与 `freeRTOS/Src`

[user_sources.cmake](../user_sources.cmake)：

```cmake
file(GLOB_RECURSE USER_SOURCES
    "${CMAKE_CURRENT_SOURCE_DIR}/Core/Src/*.c"
    "${CMAKE_CURRENT_SOURCE_DIR}/freeRTOS/Src/*.c"
)
```

实际数量（本工程当前状态）：

| 目录 | .c 数量 | 内容 |
|---|---|---|
| `Core/Src` | 22 | `main.c`、中断/MSP、`app_*.c`、`pid.c`、`qmath.c`、`memory_monitor.c` 等 |
| `freeRTOS/Src` | 9 | `tasks.c`、`queue.c`、`list.c`、`timers.c`、`heap_4.c`、`port.c` 等 |

两个必须知道的机制：

1. **`GLOB_RECURSE` 会递归子目录**（`GLOB` 只匹配当前层）。
2. **GLOB 只在「配置阶段」执行一次**，结果被固化成 `build.ninja` 里的编译规则；构建阶段 Ninja 不会再看目录里多了什么。

> 本工程**没有** `CONFIGURE_DEPENDS`。所以新增一个 `Core/Src/app_xxx.c` 后，直接 `cmake --build --preset Debug` 不会编译它；必须先重新执行 `cmake --preset Debug`。这是本项目最容易踩的坑之一。

### 2.2 第 2 段：为什么必须排除 `system_stm32f1xx.c`

```cmake
list(REMOVE_ITEM USER_SOURCES
    "${CMAKE_CURRENT_SOURCE_DIR}/Core/Src/system_stm32f1xx.c"
)
```

因为 `Core/Src` 里的 `system_stm32f1xx.c` 已经由**另一个目标** `STM32_Drivers`（OBJECT 库）编译：

```text
build/Debug/build.ninja:
cmake/stm32cubemx/CMakeFiles/STM32_Drivers.dir/__/__/Core/Src/system_stm32f1xx.c.obj
```

如果再被 `user_sources.cmake` 收一次，就是两个目标各编一份，链接时报 `multiple definition`。

那为什么 `main.c`、`stm32f1xx_it.c` 等也被 GLOB 收到，却没有重复定义？

- 它们同时出现在 `MX_Application_Src` 和 `user_sources.cmake` 里，但这两个列表都属于**同一个可执行目标** `CARTESTFreertos`。
- CMake 会把同一条源文件路径归一化、去重，所以只生成一条编译规则。
- `system_stm32f1xx.c` 属于**另一个目标** `STM32_Drivers`，去重管不到，必须手工排除。

**原则：每个 `.c` 只能有一个「负责编译它的目标」。**

### 2.3 第 3 段：源文件和头文件挂到目标上

```cmake
target_sources(${CMAKE_PROJECT_NAME} PRIVATE ${USER_SOURCES})

target_include_directories(${CMAKE_PROJECT_NAME} PRIVATE
    "${CMAKE_CURRENT_SOURCE_DIR}/Core/Inc"
    "${CMAKE_CURRENT_SOURCE_DIR}/freeRTOS/Inc"
)
```

| 目录 | 里面的头文件 |
|---|---|
| `Core/Inc` | `main.h`、`app_*.h`、`pid.h`、`lpf.h`、`qmath.h`、`memory_monitor.h` 等 |
| `freeRTOS/Inc` | `FreeRTOS.h`、`task.h`、`queue.h`、`semphr.h`、`FreeRTOSConfig.h`、`portmacro.h` 等 |
| `Drivers/...` | 由 `cmake/stm32cubemx/CMakeLists.txt` 的 `stm32cubemx` INTERFACE 目标提供，不在这里重复写 |

三个要点：

1. **CMake 不会递归搜索 include 目录**：只把列出的目录直接放进 `-I`，子目录要单独写。漏掉的典型报错是 `fatal error: xxx.h: No such file or directory`。
2. `PRIVATE` 表示这些路径只给当前目标用，不会传播给依赖它的目标。
3. 用 `target_include_directories` 而不是全局 `include_directories`，作用范围限定在目标上。

### 2.4 本工程没有的东西：预编译库、`-u _printf_float`

- 没有链接预编译 `.a`（FreertosGUILab 的 `lcd.a` 那种）。
- 链接选项里没有 `-u _printf_float`；`Core/Src` 里也没有 `%f` 打印。
- 日志用 `App_USART2_Printf()` 里的 `vsnprintf`，只格式化整数/字符串，newlib-nano 够用。

如果以后要 `printf("%f", x)`，需要额外加 `-u _printf_float`，否则浮点格式化代码不会被链入，输出会为空或异常。

### 2.5 一张表记住每段职责

| 段落 | 做什么 | 删掉/改错的后果 |
|---|---|---|
| `GLOB_RECURSE` | 收集 `Core/Src` + `freeRTOS/Src` 的 `.c` | 相关源文件不编译 → `undefined reference` |
| `REMOVE_ITEM` | 排除 `system_stm32f1xx.c` | 两个目标各编一份 → `multiple definition` |
| `target_sources` | 把源文件挂到可执行目标 | 同上 |
| `target_include_directories` | 给编译器 `-I` 路径 | 头文件找不到，编译失败 |
| `CONFIGURE_DEPENDS` | 本工程**没有** | 新增 `.c` 后必须手动 `cmake --preset Debug` |

### 2.6 易错点清单

- **新增 `.c` 后忘了重新配置**：只 `cmake --build` 不会重新 GLOB，新文件不参与编译；调用方会报 `undefined reference`。
- **两个目标编译同一个 `.c`**：`system_stm32f1xx.c` 就是例子。
- **头文件目录漏列**：CMake 不递归，新增目录必须改 `user_sources.cmake`。
- **删除了 `.c` 没重新配置**：Ninja 仍指向旧文件，报 `missing and no known rule to make it`。
- **想加 `CONFIGURE_DEPENDS`**：可以，构建前会自动重扫目录；代价是每次构建多一次目录扫描。

## 第三部分：复位原因 POWER-ON / PIN / SOFTWARE / IWDG / WWDG / LOWPOWER 怎么来的

这条链路分三层：**硬件置位 → 固件翻译 → 读后即清**。

### 3.1 硬件层：`RCC_CSR` 里的一组「粘滞位」

STM32F1 的 `RCC->CSR` 寄存器里有一组复位标志位（位定义见 [stm32f103xb.h](../Drivers/CMSIS/Device/ST/STM32F1xx/Include/stm32f103xb.h) 第 1406–1426 行）：

| 位 | 宏 | 含义 |
|---|---|---|
| 31 | `RCC_CSR_LPWRRSTF` | 低功耗管理复位 |
| 30 | `RCC_CSR_WWDGRSTF` | 窗口看门狗复位 |
| 29 | `RCC_CSR_IWDGRSTF` | 独立看门狗复位 |
| 28 | `RCC_CSR_SFTRSTF` | 软件复位 |
| 27 | `RCC_CSR_PORRSTF` | 上电/掉电复位 |
| 26 | `RCC_CSR_PINRSTF` | NRST 引脚复位 |
| 24 | `RCC_CSR_RMVF` | 写 1 清除上面所有标志 |

两个性质决定用法：

1. **粘滞（sticky）**：复位发生时硬件把对应位置 1，之后一直保持，断电才丢；软件不清，它就一直是 1。
2. **只能整体清**：写 `RMVF=1` 一次性清掉全部复位标志，不能只清某一位。

### 3.2 固件层：按「最具体优先」翻译成字符串

[main.c](../Core/Src/main.c#L116-L126) 第 116–126 行：

```c
static const char *prvResetCause(void)
{
  if (__HAL_RCC_GET_FLAG(RCC_FLAG_IWDGRST)  != RESET) { return "IWDG"; }
  if (__HAL_RCC_GET_FLAG(RCC_FLAG_WWDGRST)  != RESET) { return "WWDG"; }
  if (__HAL_RCC_GET_FLAG(RCC_FLAG_LPWRRST)  != RESET) { return "LOWPOWER"; }
  if (__HAL_RCC_GET_FLAG(RCC_FLAG_SFTRST)   != RESET) { return "SOFTWARE"; }
  if (__HAL_RCC_GET_FLAG(RCC_FLAG_PORRST)   != RESET) { return "POWER-ON"; }
  if (__HAL_RCC_GET_FLAG(RCC_FLAG_PINRST)   != RESET) { return "PIN"; }
  return "UNKNOWN";
}
```

两个设计点：

- 返回字符串常量（存在 Flash 里），后面清寄存器不会让结果失效。
- **if 链的顺序就是优先级**，从「最具体」排到「最泛化」，`PIN` 必须放最后。

#### `__HAL_RCC_GET_FLAG` 到底做了什么

它不是直接读 `RCC->CSR`，而是把「寄存器索引 + 位号」编码成一个字节（[stm32f1xx_hal_rcc.h](../Drivers/STM32F1xx_HAL_Driver/Inc/stm32f1xx_hal_rcc.h#L1129-L1131)）：

```c
#define __HAL_RCC_GET_FLAG(__FLAG__) (((((__FLAG__) >> 5U) == CR_REG_INDEX) ? RCC->CR : \
                                      ((((__FLAG__) >> 5U) == BDCR_REG_INDEX) ? RCC->BDCR : \
                                                                                RCC->CSR)) \
                                      & (1U << ((__FLAG__) & RCC_FLAG_MASK)))
```

- 高 3 位是寄存器索引：1=CR、2=BDCR、3=CSR（`CSR_REG_INDEX` 定义在第 1293 行）。
- 低 5 位是位号（`RCC_FLAG_MASK = 0x1F`，第 1295 行）。
- `RCC_FLAG_IWDGRST` 就是 `(3 << 5) | 29`，所以最终落到 `RCC->CSR` 的第 29 位。

### 3.3 为什么 `PIN` 必须放最后（最容易踩的坑）

`PINRSTF` 表示「复位信号作用到了 NRST 引脚」。而在 STM32F1 上，其它复位源（上电、看门狗、软件复位）产生的内部复位**也会经过 NRST 复位逻辑**，所以实际读出来常常是多个位同时为 1：

- 上电后可能 `PORRSTF + PINRSTF` 都为 1；
- 看门狗复位后可能 `IWDGRSTF + PINRSTF` 都为 1。

如果代码把 `PIN` 写在最前面，就会永远输出 `PIN`，看门狗复位永远查不出来。同理 `POWER-ON` 也要排在 `PIN` 前面。**这段代码看起来「顺序随意」，实际顺序是正确性的一部分。**

### 3.4 时序层：先读、再打印、最后清

[main.c](../Core/Src/main.c#L128-L140) 第 128–140 行：

```c
static void prvPrintBootInfo(void)
{
  char line[96];
  int n = snprintf(line, sizeof(line), "fw %s | build %s %s | reset %s\r\n",
                   FW_VERSION, __DATE__, __TIME__, prvResetCause());
  if (n > 0)
  {
    if (n > (int)sizeof(line) - 1) { n = (int)sizeof(line) - 1; }
    HAL_UART_Transmit(&huart2, (uint8_t *)line, (uint16_t)n, 50);
  }
  __HAL_RCC_CLEAR_RESET_FLAGS();
}
```

调用点在 [main.c](../Core/Src/main.c#L184-L188)，位于 USART2 初始化之后、`B1` 之前、调度器启动之前。

执行顺序：

```
上电/复位
  │  硬件置位 RCC->CSR 对应 bit
  ▼
MX_USART2_UART_Init()          ← 先让打印通道可用
  ▼
prvResetCause()                ← 1. 读：取复位原因
  ▼
snprintf()                     ← 2. 把原因复制进 line[] 字符串
  ▼
HAL_UART_Transmit()            ← 3. 阻塞打印（不依赖 FreeRTOS/DMA）
  ▼
__HAL_RCC_CLEAR_RESET_FLAGS()  ← 4. 清：写 RMVF，把粘滞标志归零
```

关键只有一条：**读必须在清之前**。打印在前还是在后不影响结果，因为 `prvResetCause()` 返回的是字符串常量，`snprintf` 已经把它复制进 `line[]`，清寄存器不会改字符串。

`__HAL_RCC_CLEAR_RESET_FLAGS()` 的实现只有一句：通过位带别名把 `RCC_CSR_RMVF` 写 1（[stm32f1xx_hal_rcc.h](../Drivers/STM32F1xx_HAL_Driver/Inc/stm32f1xx_hal_rcc.h#L1104)）。

### 3.5 为什么「不清就会误报」——一个具体例子

假设第一次复位是看门狗咬的，`IWDGRSTF=1`。如果没有清标志：

1. 用户按了一下复位键，`PINRSTF` 也被置 1；
2. 此时 `RCC->CSR` 里 `IWDGRSTF` 和 `PINRSTF` 同时为 1；
3. `prvResetCause()` 按优先级先命中 `IWDG`，于是打印 `reset IWDG`。

但这次真正的原因是按键复位，看门狗是**上一次**的事。清掉之后，下一次复位寄存器里只会留下本次真正触发的那一位。

### 3.6 本工程的 IWDG 为什么约 410 ms

[main.c](../Core/Src/main.c#L428-L449) 的 `MX_IWDG_Init()`：

```c
hiwdg.Instance = IWDG;
hiwdg.Init.Prescaler = IWDG_PRESCALER_4;
hiwdg.Init.Reload = 4095;
HAL_IWDG_Init(&hiwdg);
```

计算：

- LSI ≈ 40 kHz；
- 预分频 4 → 计数时钟 ≈ 10 kHz；
- 重装值 4095 → 4096 / 10 kHz ≈ **409.6 ms**。

谁在喂狗：

- 调度器启动前，`main()` 在 MPU 初始化后手动 `HAL_IWDG_Refresh(&hiwdg)` 一次；
- 调度器启动后，`MemMon` 任务每 **100 ms** 喂一次（[memory_monitor.c](../Core/Src/memory_monitor.c#L47-L49)，`MONITOR_FEED_INTERVAL_MS = 100`）。

所以：

- 看到反复 `reset IWDG`，先查 MemMon 是否还在跑、是否有长时间阻塞（I2C 死等、Flash 擦除、断点暂停）；
- 调试时 `__HAL_DBGMCU_FREEZE_IWDG()` 会在 CPU 暂停时冻结 IWDG，避免一停就被复位；
- **清复位标志 ≠ 关看门狗**：`CLEAR_RESET_FLAGS` 只清历史记录，IWDG 启动后该喂还得喂。

### 3.7 这些原因码在排查时怎么用

| 输出 | 说明 | 排查方向 |
|---|---|---|
| `POWER-ON` | 正常上电 | 无异常 |
| `PIN` | NRST 引脚被拉低 | 按了复位键 / 下载器复位 / 复位电路干扰 |
| `SOFTWARE` | 软件复位 | 代码里调了 `NVIC_SystemReset()`，或调试器执行了复位 |
| `IWDG` | 独立看门狗溢出 | 程序跑飞或卡死，某处没喂狗 |
| `WWDG` | 窗口看门狗溢出 | 喂狗时机不对（本工程未启用 WWDG） |
| `LOWPOWER` | 低功耗管理复位 | 进低功耗流程 / 选项字节相关配置 |
| `UNKNOWN` | 一个标志都没命中 | 寄存器读取异常，先怀疑时钟/调试链路 |

### 3.8 延伸易错点

- **`__DATE__` / `__TIME__` 是「编译 main.c 的时刻」**：增量构建没重新编译 `main.c` 时，版本行的日期时间是旧的。要绝对准确，应由构建系统传入 `-DFW_BUILD_TIME=...`。
- **`FW_VERSION` 是「配置阶段的 git describe」**：改完代码只 `cmake --build` 不重新 configure，版本号可能还是旧的；提交后也要重新配置才会更新。
- **调试器 attach 也会改现场**：连接调试器时的复位/暂停可能产生新的 `SOFTWARE`/`PIN` 标志，看复位原因最好在纯上电场景下观察。
- **打印窗口很短**：如果复位后立刻又复位，串口可能只输出半行。看到「反复重启 + 半行乱码」时，先看 reset 原因是不是 `IWDG`。

## 三句话背下来

- **构建**：预设绑定工具链文件，工具链只假设编译器在 PATH，HAL/CMSIS 以 `Drivers/` 相对路径随 git 提供 —— 所以 clone + 装工具链即可构建，CubeMX 只用来改 `.ioc`。
- **用户源码**：`user_sources.cmake` 用 GLOB 收 `Core/Src` + `freeRTOS/Src`，排除 `system_stm32f1xx.c`（它归 `STM32_Drivers` 目标），再把源文件和 include 路径挂到可执行目标；原则是「每个 `.c` 只能有一个编译它的目标」，且 **GLOB 只在配置阶段生效——本工程没加 `CONFIGURE_DEPENDS`，新增 `.c` 必须手动重新 configure**。
- **复位原因**：硬件把复位源写进 `RCC->CSR` 的粘滞位，固件**先读、按「具体优先、PIN 最后」翻译、再清 RMVF**，这样每次打印的都是本次复位原因；IWDG 约 410 ms，MemMon 每 100 ms 喂一次。
