# 学习笔记：一个 STM32 工程怎么做“交付”（SOP）

> 这份笔记只讲一件事：**怎么把一个“我电脑上能跑的工程”变成“别人拿到也能跑、且有证据”的交付物。**
> 以 `CARTESTFreertos` 为示范，命令和结果都是这台机器上真实跑过的。
> CubeMX 再生成的细节是附录，不是主线；主线是下面七步。

---

## 0. 先把“交付”这个词说清楚

很多人以为交付 = 代码写完 / 我电脑能跑 / 发个压缩包。都不对。

**交付 = 别人 clone 下来能编、能烧、能看到预期现象，并且你能拿出一页证据说明“我测过”。**

判断交付是否成立，只问三句：

| 问题 | 对应动作 | 不成立的后果 |
|---|---|---|
| **别人能编吗？** | 空目录 clone + 从零构建 | 面试官/同事第一步就卡住 |
| **别人能跑吗？** | 烧录 + 首行日志 + 操作说明 | 编出来也不知道对不对 |
| **别人能信吗？** | 构建基线 + 实测记录 + 变更记录 | 只能算“看起来能跑” |

> 一句话：**交付不是“完成”，是“可复现 + 有证据”。**

---

## 1. 交付物清单：做完这些才算完

| # | 交付物 | 放在哪 | 验收标准 |
|---|---|---|---|
| 1 | 可构建的仓库 | Git 仓库 | 空目录 clone 后 0 error 0 warning |
| 2 | README | 仓库根目录 | 陌生人 5 分钟能编、能烧、能看到现象 |
| 3 | 环境说明 | `docs/env.md` | 工具链版本、体检命令、缺什么怎么补 |
| 4 | 构建基线 | `docs/构建基线.md` | 三构型 FLASH/RAM 数字 + 复现命令 |
| 5 | 启动自报家门 | 固件首行 | 版本 / 构建时间 / 复位原因 |
| 6 | 一页实测记录 | `docs/调试记录_*.md` | 现象 → 假设 → 测量 → 改动 → 复测 |
| 7 | 变更记录 | `docs/变更记录_*.md` | 改前 / 改后 / 原因 / 验证结果 |
| 8 | 干净的 Git 状态 | `git status` | 无未提交改动，提交按批次 |

**最小交付**：1 + 2 + 8。
**完整交付**：1–8 全有。面试能拿得出手的是完整交付。

## 2. 七步 SOP

### 第 1 步：冻结基线（先别改代码）

**做什么**

1. `git status` 确认没有无关改动；有就先提交或 stash。
2. 记下当前提交号，打一个 tag（可选但推荐）。
3. 开一个分支做本次交付，不要直接在 main 上边改边交付。

**命令**

```powershell
git status --short
git log --oneline -5
git tag
git switch -c delivery/2026-11-17   # 名字按日期或阶段
```

**通过标准**

- `git status` 干净，或剩下的改动明确属于本批。
- 你知道“交付前”的提交号，出问题能回退。

**常见坑**

- 把 IDE 自动写入的文件（如 `.code-workspace` 的 workspaceId）混进交付提交。
- 构建目录 `build/` 被误提交。

---

### 第 2 步：干净环境构建（交付的核心）

**为什么要 clone 到空目录**

你现在的 `build/` 里有缓存、有旧对象文件、有本机路径。**“我这儿能编”不代表“别人能编”。**
唯一可信的验证是：换一个空目录，从 `git clone` 开始，重新配置、重新编译。

**命令**

```powershell
$tmp = Join-Path $env:TEMP "deliver_check"
if (Test-Path $tmp) { Remove-Item -Recurse -Force $tmp }

git clone <你的仓库地址> $tmp
Set-Location $tmp

cmake --preset Debug
cmake --build --preset Debug
```

**通过标准**

- **0 error、0 warning**。
- 生成 `.elf`，构建日志里有 FLASH/RAM 占用。
- 版本号能正常注入（有 `.git` 时是 `git describe`，没有时是 `dev`）。

**本工程的真实结果**

```text
Firmware version: baseline-2026-11-16-4-g85669a3
Debug: FLASH 49,704 B (75.84%) / RAM 14,512 B (70.86%)
0 error 0 warning
```

**常见坑**

| 现象 | 原因 | 处理 |
|---|---|---|
| 本机能编，clone 后编不过 | 有文件没入库、用了本机绝对路径 | `git ls-files` 对照；把路径改成仓库相对路径 |
| clone 后 warning 一堆 | 本机 `build/` 缓存掩盖了 warning | 删掉 `build/` 再编；或用空目录 clone |
| 编译器找不到 | 工具链不在 PATH | 按 `docs/env.md` 体检 |

> **这一步不通过，后面所有交付都不算数。**

---

### 第 3 步：让固件“自报家门”

**做什么**

上电第一行固定打印：

```text
fw <版本> | build <日期 时间> | reset <POWER-ON/IWDG/SOFTWARE/...>
```

**为什么**

- 面试官/同事烧进去，第一眼就知道“烧的是哪版固件”。
- 出问题时能区分“上电复位 / 看门狗复位 / 软复位”，不用猜。
- 这是“能跑”的证据，不是“我觉得能跑”。

**本工程怎么做的**

- CMake 配置阶段执行 `git describe --tags --always --dirty`，注入 `FW_VERSION`。
- `main.c` 在 USART2 初始化后、调度器启动前，用阻塞串口打印首行。
- 打印后清复位标志，下次上电才能区分新的复位原因。

**通过标准**

- 上电到首行 **< 3 秒**。
- 复位原因能区分至少三种：上电、IWDG、软复位。
- 首行不依赖 FreeRTOS、不依赖 DMA（调度器还没启动）。

**常见坑**

- 用 `printf` 走 DMA 队列，结果调度器没启动，首行永远不出来。
- 打印后不清标志，第二次上电还显示上一次的原因。

---

### 第 4 步：写三份文档（只写“别人需要的”）

#### 4.1 README：5 分钟跑通

必须包含：

1. 这是什么（一句话）。
2. 依赖（工具链版本）。
3. 配置 + 构建命令（可直接复制）。
4. 烧录命令。
5. 串口参数 + 正常上电日志。
6. 已知限制。
7. 文档索引。

**不要**写成“项目介绍 + 技术栈 + 未来规划”。面试官只想知道“怎么跑起来”。

#### 4.2 `docs/env.md`：环境体检

- 本机实测的工具链版本。
- 逐条检查命令（gcc / cmake / ninja / openocd / 连接芯片 / 构建）。
- 缺哪项怎么补。
- 三条输出通道：串口、GDB 读 RAM、SWO（可选）。

#### 4.3 `docs/构建基线.md`：数字可复查

- 三构型（Debug / Release / MinSizeRel）的 FLASH/RAM。
- 复现命令。
- 结论：发布用哪个构型、为什么。
- 更新记录：日期 + 提交号。

**通过标准**

- 文档里的每个数字都能用命令复现。
- 文档里的每个命令都能直接复制运行。
- 没有和代码冲突的旧数字。

**常见坑**

- 代码改了，文档数字没改（本工程之前就漂移过）。
- README 写“支持 XX”，但仓库里没有对应代码。

---

### 第 5 步：做一页“实测证据”

**为什么**

“我测过”不算证据。证据必须是别人能照着走到同一个结论的东西。

**固定结构（五段）**

1. **现象**：看到了什么异常/要验证什么。
2. **假设**：如果假设成立，波形/日志应该是什么样。
3. **测量**：仪器、探头、量程、触发、测点。
4. **改动**：改了哪个文件哪一行，为什么改。
5. **复测**：同一条件下再测一次，结果与改动前对比。

**没有示波器怎么办**

- 先借实验室的。
- 实在没有：用 DWT 打点 + GPIO 翻转 + 串口时间戳做替代验证；但这只能证明代码路径，**不能替代波形证据**。

**本工程现状**

- 模板已建：`docs/调试记录_示波器实测.md`。
- 有板无仪器：这一条仍待实测，不能算完成。

---

### 第 6 步：仓库卫生

| 项 | 做什么 | 本工程结果 |
|---|---|---|
| 死代码 | 删除无调用者的文件/函数 | 删除 `app_sys.c` |
| 重复文件 | 两份链接脚本要注明哪份生效 | `STM32F103xx_FLASH.ld` 顶部注明只用于 ARMClang |
| 文档漂移 | 用构建输出核对数字 | README/构建基线/内存分布已刷新 |
| `.gitignore` | 排除 `build/`、`*.elf`、`*.map` | 已排除 |
| 提交规范 | Conventional Commits，中文描述 | `chore(delivery): ...` |
| 批次 | 一批一提交，代码和文档分开 | 3 个 commit |

**通过标准**

- `git status` 干净。
- `git log` 里每个提交只做一件事，能看懂。
- 仓库里没有“不知道该不该留”的文件。

---

### 第 7 步：验收与交接

**五条验收（少一条都不算完整交付）**

| # | 验收项 | 本工程状态 |
|---|---|---|
| 1 | 空目录 clone，0 error 0 warning | 通过 |
| 2 | 陌生人按 README 5 分钟跑通 | 自测通过，待他人实测 |
| 3 | 上电首行 < 3 s，复位原因可区分 | 代码已实现，待上板 |
| 4 | 提交只含本阶段文件，`git status` 干净 | 通过 |
| 5 | 一页实测记录 | 待实测 |

**交付汇报固定格式**

```text
本批提交：<commit hash>
修改文件：<列表>
验收结果：<哪几条通过、哪几条没通过>
残留风险：<没板子/没仪器/未提交的其它仓库>
下一批内容：<下一步做什么>
```

> 不要只说“做完了”。要说“哪几条通过、证据在哪、哪几条还没通过”。

## 4. 交付时不要做的事

| 不要 | 为什么 |
|---|---|
| 边交付边加功能 | 一出问题分不清是交付改动还是新功能 |
| 把 `build/`、`.elf`、`.map` 提交进去 | 仓库膨胀，且换机器无意义 |
| 只测“我这儿能跑” | 别人 clone 后可能编不过 |
| 文档数字靠记忆 | 一定漂移；用构建输出核对 |
| 把两个项目混进一个仓库 | 交付证据互相污染（比如 CAN 不要塞进平衡车） |
| 没仪器就写“已实测” | 面试一问就穿帮 |
